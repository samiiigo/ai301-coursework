# Plan for issue #40 — Public read-only review links

Issue: https://github.com/codepath/pathreview-ai301-fa26-s3/issues/40

Baseline reproduction: https://github.com/codepath/pathreview-ai301-fa26-s3/issues/40#issuecomment-5922456109
Implementation branch: `fix/40-public-review-links` in `samiiigo/pathreview-ai301-fa26-s3`.

## Diagnosis

My reproduction showed that the current Share action is not creating a public share link. It only copies the normal authenticated review URL.

The evidence I am relying on is:

> `ReviewPage.tsx` uses `window.location.href` in the Share handler, so it copies the current authenticated review URL directly.

and:

> `/reviews/:reviewId` is wrapped in `ProtectedRoute`, which prevents unauthenticated users from viewing the review page.

I also found:

> `frontend/src/services/shareService.ts`, which is referenced by the issue, does not currently exist in the repository.

and:

> `api/routes/reviews.py` does not contain a public or token-based endpoint for accessing a shared review.

That explains the reproduced behavior: the copied URL is the same private route used by the signed-in owner, so opening it without a session redirects to login. There is also no share token or expiry mechanism, so the requested 30-day expiration cannot happen in the current implementation.

## Scope

### In scope

- Generate a separate share token for a completed review after verifying that the signed-in user owns the review.
- Make the token expire after 30 days.
- Add an unauthenticated API path that accepts a valid share token and returns the review summary read-only.
- Add a frontend service for creating a share link and loading a shared review.
- Change the current Share button so it copies the new public URL rather than `window.location.href`.
- Add an unprotected frontend route/page for viewing a valid shared review.
- Add tests for successful sharing, unauthenticated viewing, invalid/expired tokens, and the Share button behavior.

### Out of scope

- Making the existing `/reviews/:reviewId` owner route public.
- Changing login/authentication behavior for normal review pages.
- Adding link revocation, custom expiration periods, analytics, permissions beyond read-only access, or a share-management UI.
- Redesigning the review page or doing unrelated cleanup/refactors.

## Files I expect to touch

- `api/routes/reviews.py`
  - Add an authenticated endpoint that creates a 30-day share token after ownership is verified.
  - Add an unauthenticated endpoint that validates a share token and returns the referenced review.
- `api/schemas/review.py`
  - Add share-token and public-summary response schemas. The public response contains only score and feedback; it excludes profile identifiers and internal errors.
- `core/services/share_service.py` (new)
  - Create and validate signed share tokens with a required expiry and a dedicated purpose claim. Use a `review_id` claim and no authentication `sub` claim so share links cannot act as login credentials.
- `core/services/review_service.py`
  - Add a narrow lookup used by the public-token path so the shared endpoint can fetch the review by id without changing the existing owner-checked `get_review`.
- `frontend/src/services/shareService.ts` (new)
  - Create the share link through the API and fetch a review through the public token endpoint.
- `frontend/src/pages/ReviewPage.tsx`
  - Replace the current `window.location.href` clipboard behavior with the public link returned/generated by the share service.
- `frontend/src/pages/SharedReviewPage.tsx` (new)
  - Render the shared review in a read-only view without owner-only controls.
- `frontend/src/App.tsx`
  - Register the shared-review route outside `ProtectedRoute`.
- Focused backend/frontend test files following the repository's existing test layout.

I do not expect to add a database migration. The first implementation approach is to use the repository's existing signed JWT utilities with a dedicated share-purpose claim and a 30-day expiry. If the existing security helper cannot safely distinguish share tokens from login tokens, I will add the smallest helper/validation needed rather than storing share state in the database.

## Approach

1. Add share-token generation on the backend.
   - The create-share endpoint remains authenticated.
   - It looks up the review using the existing owner-checked path.
   - It creates a signed token containing the review id plus a claim that identifies it as a review-share token.
   - It uses a 30-day expiration.

2. Add public-token validation and review retrieval.
   - The public endpoint does not depend on `get_current_user`.
   - It decodes the token, verifies that it is a review-share token, verifies that it contains a review id, and relies on token expiry validation.
   - Invalid, malformed, wrong-purpose, or expired tokens return an error instead of review data.
   - A valid token loads only the completed review referenced by the token and returns only score and feedback through the public-summary schema.
   - Require an expiry claim and validate the review id as a UUID. The creation route rejects incomplete reviews. Public retrieval rejects missing or no-longer-complete reviews.

3. Add the frontend share service.
   - Authenticated creation calls the create-share endpoint.
   - The service builds/returns a public URL under a dedicated shared-review route.
   - Public loading calls the unauthenticated shared-review API endpoint.

4. Update the Share button.
   - `ReviewPage.tsx` requests a public link for the current review.
   - It copies that public URL to the clipboard.
   - Failure to create/copy the link shows an error instead of claiming the link was copied.

5. Add a public read-only route.
   - `App.tsx` registers a route such as `/shared/reviews/:token` outside `ProtectedRoute`.
   - `SharedReviewPage.tsx` loads the review by token and renders the review score/feedback without edit/owner-only actions.

6. Add focused tests, then run the repository-required checks from `docs/CONTRIBUTING.md`.

### Expiry and invalid-token checks

I will add automated coverage that verifies:

- A newly generated share token carries a 30-day expiration.
- A valid, unexpired share token can fetch the correct review without authentication.
- An expired token is rejected.
- A malformed token is rejected.
- A valid login token or other wrong-purpose token cannot be used as a share token.
- A share token cannot authenticate as a user on a protected endpoint.
- Missing-expiry, invalid-review-id, and tampered-signature tokens are rejected.
- Creation requires authentication and ownership, and rejects incomplete reviews.
- The public response excludes profile identifiers and internal errors.
- A token for a missing review does not expose another review.

## Risks and unknowns

- The existing JWT helpers are also used for authentication. I need to ensure a share token is distinguishable by a dedicated purpose/type claim so a normal login token cannot be accepted by the public-share endpoint.
- The current authentication middleware reads `sub` as the user id. Share tokens will omit `sub`, and a regression test will verify they cannot authenticate on protected routes.
- I have not yet confirmed the preferred HTTP status for expired/invalid share tokens in this repository. I will follow the nearest existing API convention while implementing.
- The issue says the link expires after 30 days but does not require revocation. A signed expiring token should satisfy the stated behavior without persistence; if implementation evidence shows persistence is required by an existing convention, I will record that as a deviation before expanding scope.
- I will keep the normal authenticated review route unchanged so the new public access path does not weaken ownership checks.
