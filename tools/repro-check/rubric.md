# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| steps-complete | The repro report's steps, read against the input, command, flags, and configuration the issue itself gives to work from | Pass if a stranger holding only this package could run the steps top to bottom and land on the same run: every file's contents are shown or fully pinned down (not merely paraphrased in a way that could vary the result), and every command, flag, and setting needed is given, with no step depending on material the reader cannot obtain (a private repo, an unshared config, a resource the issue itself never pastes the content of). A detail the report leaves to the reader passes when it plainly cannot change whether the failure triggers (which package names fill an otherwise-valid list); it fails when the missing or swapped detail is exactly what decides the outcome — whether the failure actually fires is `artifact-matches-claim`'s question, not this one. Fail if a material step has to be invented, if the run depends on unobtainable material, or if a file's exact content is only paraphrased where the paraphrase could change the result. | required |
| environment-info | The repro report's environment record, read against the version and platform the issue targets | Pass if the record names the tool or package version that was run AND the OS or platform it ran on, and that version and platform are the ones the issue targets — or the difference is stated in the report. Fail if either is missing, or a difference is present but never mentioned. | required |
| artifact-present | The repro report's shown output: command transcripts, log excerpts, screenshots, measurements — produced by the author's own run | Pass if the report shows at least one artifact that came out of running the steps. Fail if the outcome is only asserted ("I verified this", "guaranteed reproducible", "same here"), or if the only output shown is setup noise (version banners, a process starting) that does not bear on the behavior in question. | required |
| artifact-matches-claim | The artifact, read against both the behavior the issue describes and the conclusion the report draws from it | Pass if exactly one of these holds: (a) the report concludes the issue reproduces, and the artifact shows the issue's own failure — the same error, crash, exit, or wrong output the issue names, not an adjacent failure of the same tool; or (b) the report concludes it could not reproduce, and the artifact shows the attempt that came up empty, with what differed named. Fail if the artifact shows a different failure than the issue describes while the report presents it as confirmation, or if the conclusion is more certain or more general than the shown output supports. | required |
| expected-vs-actual | The repro report's statement of outcome, read against the issue's description of correct behavior and, for a report that could not reproduce, against the failure the issue predicts | Pass if the report states both what should happen and what did, and the two are distinguishable from each other and from the artifact. For a report that concludes the issue reproduces, "expected" must be the project's correct behavior and "actual" the bug shown — stated the other way round is a fail. For a report that concludes it could not reproduce, "expected" is properly the failure the issue describes and "actual" is the normal behavior actually observed; that is the correct shape for a negative result, not a reversal. Fail if only one side is given, or if an artifact is shown without saying which side of it is the defect. | required |
| claim-is-specific | The candidate claim comment, read against the issue body and thread highlights | Pass if the comment could only have been written about this issue — it names the behavior, the version reproduced on, or a fact from the thread — and commits only to work the author has already done or names as their next step. Fail if it is interchangeable with a comment on any other issue ("+1", "please assign me"), promises a fix by a guaranteed date, or asks for the issue to be reserved or held. | required |
| ai-disclosure | The repo-facts contribution-policy line, read against both candidate comments | Treat the package as AI-assisted work. Pass if the repo's stated policy does not require disclosing AI assistance in issue comments. If the policy does require it, pass only if one of the comments states the assistance and its extent. Fail only on that combination: a policy that requires disclosure in comments, and comments that do not disclose. | required |

## Verdict rule

Ready (accept) only if every required check passes. Any required check
graded fail holds the package (reject). `unclear` counts as a fail:
proof that cannot be verified from the package is not proof that is
ready to post. Preferred checks never change the verdict.
